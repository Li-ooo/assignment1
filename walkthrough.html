Command Line Shopping Cart

01

Why the code is split into three files

The assignment asks for code that is easy to unit-test. The readline loop is impossible to test without mocking stdin, so it is kept separate from every piece of business logic. products.js holds the catalog, cart.js holds pure functions that operate on cart arrays, and index.js only prints menus and wires user input to those functions.

assignment1-shopping-cart/ ├── src/ │ ├── products.js # catalog data + findProductById() │ ├── cart.js # createCart / addToCart / calculateTotal / checkout │ └── index.js # readline CLI — UI glue only ├── test/ │ └── cart.test.js # vitest suite ├── package.json └── Dockerfile
Design rule: every function in cart.js takes the cart array and the catalog array as arguments instead of closing over module-level constants. That means a test can hand it a fresh, cloned catalog and checkout mutations never leak into the next test.
02

products.js — catalog data and lookup

The catalog is a plain array of objects, exactly as the spec requires: id, name, description, price, quantityAvailable. One product (id 5) starts with quantityAvailable: 0 on purpose, so we have an out-of-stock edge case to test.

src/products.js
export const PRODUCTS = [
  { id: 1, name: 'Classic T-Shirt',   description: '100% cotton, unisex', price: 199.99, quantityAvailable: 10 },
  { id: 2, name: 'Coffee Mug',         description: 'Ceramic, 350 ml',     price: 49.90,  quantityAvailable: 25 },
  { id: 3, name: 'Wireless Mouse',     description: 'Ergonomic, 2.4 GHz',  price: 249.00, quantityAvailable: 8 },
  { id: 4, name: 'Lined Notebook A5', description: '96 pages, hard cover', price: 29.50,  quantityAvailable: 50 },
  { id: 5, name: 'Desk Lamp',          description: 'LED, adjustable arm',  price: 129.00, quantityAvailable: 0 }
]

export function findProductById(products, id) {
  if (!Array.isArray(products)) return null
  return products.find(p => p.id === id) || null
}

What to say in the video

  • findProductById returns null instead of undefined so callers can use a strict if (!product) check.
  • It takes the catalog as an argument rather than referencing PRODUCTS directly, which is what lets tests clone the catalog per test case.
03

cart.js — the core logic

Four small functions. Every mutation goes through a single entry point, and validation happens in a fixed order: product exists → quantity is a positive integer → enough stock left.

createCart()

Returns a fresh empty array. Trivial, but it keeps the rest of the code from using a shared literal.

addToCart(cart, products, productId, quantity)

src/cart.js (core)
export function addToCart(cart, products, productId, quantity) {
  const product = findProductById(products, productId)
  if (!product) {
    return { success: false, error: `Product with id ${productId} does not exist.` }
  }
  if (!Number.isInteger(quantity) || quantity <= 0) {
    return { success: false, error: 'Quantity must be a positive integer.' }
  }

  const existing = cart.find(item => item.productId === productId)
  const alreadyInCart = existing ? existing.quantity : 0
  if (alreadyInCart + quantity > product.quantityAvailable) {
    return { success: false, error: `Only ${product.quantityAvailable} of '${product.name}' available` }
  }

  if (existing) {
    existing.quantity += quantity
    existing.totalPrice = money(existing.quantity * product.price)
  } else {
    cart.push({ productId, quantity, totalPrice: money(quantity * product.price) })
  }
  return { success: true }
}
  • Returns a result object { success, error? } instead of throwing, so the CLI can print the message and the tests can assert on it cleanly.
  • If the same product is added twice, the second call accumulates quantity and recomputes totalPrice on the existing line — no duplicate lines.
  • The stock check uses alreadyInCart + quantity, not just quantity, so adding 6 then 3 of a product with 8 in stock correctly fails on the second add.
  • money(n) rounds to 2 decimals to dodge floating-point drift (0.1 + 0.2 style bugs).

calculateTotal(cart)

export function calculateTotal(cart) {
  return money(cart.reduce((sum, item) => sum + item.totalPrice, 0))
}

Sums each line's totalPrice (the line price is already stored on the cart item, as the spec requires) and rounds. Empty cart → 0.

checkout(cart, products)

export function checkout(cart, products) {
  if (!Array.isArray(cart) || cart.length === 0) {
    return { success: false, error: 'Cannot checkout an empty cart.' }
  }
  const total = calculateTotal(cart)
  for (const item of cart) {
    const product = findProductById(products, item.productId)
    if (product) product.quantityAvailable -= item.quantity
  }
  const snapshot = cart.map(item => ({ ...item }))
  return { success: true, total, items: snapshot }
}
The one intentional side effect: checkout decreases quantityAvailable on the catalog objects, exactly as the spec demands. Tests work around this by cloning the catalog in beforeEach, so a checkout in test A never bleeds into test B.
04

index.js — the readline interface

This file never contains business rules. It prints the product list, parses one of four commands (add <id> <qty>, cart, checkout, quit), and calls into cart.js. After every action it loops back and prints the menu again — that satisfies the "looping" requirement.

src/index.js (parsing, simplified)
const match = line.trim().toLowerCase().match(/^add\s+(\d+)\s+(\d+)$/)
if (match) {
  const result = addToCart(cart, PRODUCTS, Number(match[1]), Number(match[2]))
  if (result.success) console.log('Added.')
  else console.log(`Could not add: ${result.error}`)
}
  • Input parsing is a single regex so garbage input falls through to the "Unknown command" branch.
  • quit closes readline; checkout prints the total and then reprints the product menu so the user can keep shopping after a failed (empty-cart) checkout.

Vitest test suite

The suite groups tests by the function under test. The most important pattern is in beforeEach: every test starts from a fresh, cloned catalog so the side effect of checkout cannot leak.

test/cart.test.js (setup)
import { describe, it, expect, beforeEach } from 'vitest'
import { PRODUCTS } from '../src/products.js'
import { createCart, addToCart, calculateTotal, checkout } from '../src/cart.js'

let catalog
beforeEach(() => {
  catalog = PRODUCTS.map(p => ({ ...p }))   // fresh clone per test
})

The two tests worth spending the most time on
it('fails when the accumulated cart quantity would exceed stock', () => {
  const cart = createCart()
  addToCart(cart, catalog, 3, 6)
  const result = addToCart(cart, catalog, 3, 3)  // 6 + 3 = 9 > 8
  expect(result.success).toBe(false)
})

it('returns the correct total and decreases stock', () => {
  const stockBefore = catalog.find(p => p.id === 1).quantityAvailable
  const cart = createCart()
  addToCart(cart, catalog, 1, 3)
  const result = checkout(cart, catalog)
  expect(result.total).toBeCloseTo(599.97, 2)
  expect(catalog.find(p => p.id === 1).quantityAvailable).toBe(stockBefore - 3)
})

The first one is the trickiest edge case: a naive implementation that only compares the new quantity against stock would accept both adds. The second one proves checkout is doing both jobs the spec asks for — computing the total and decrementing inventory.

06

Assumptions and design choices

Where the spec is ambiguous, these are the choices I made (and they are encoded in the tests):

  • Result objects, not exceptions. Validation failures return { success: false, error }. This keeps the CLI simple and makes assertions readable.
  • Same product accumulates in one line. Adding id 2 twice does not create two cart rows; it increments the existing one and recomputes totalPrice.
  • Stock check includes what is already in the cart. Otherwise a user could oversell by splitting a big order across several "add" commands.
  • Money is rounded to 2 decimals everywhere. A helper money() centralizes this so no line drifts.
  • Product id 5 starts out of stock as a fixture for the out-of-stock test.
  • ES modules ("type": "module") throughout, matching the Vite/Vitest template.
